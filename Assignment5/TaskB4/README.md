# B4 - Migration and production decision

`BusPassMigration` streams the legacy file, validates each record, logs rejected line numbers/reasons, binds accepted rows with PreparedStatement and flushes batches of 1,000 inside one transaction. A batch/SQL failure rolls back the migration; malformed legacy rows are reported separately and excluded. The program prints DatabaseMetaData product/version, JDBC driver/version, tables, and imported row count. Metadata makes portability differences visible when a deployment changes driver/server.

At approximately 800,000 annual records (100x the original 8,000) across 12 campuses and concurrent counters, use a shared relational database with unique constraints, indexes, prepared statements, transactions, and connection pooling. Text files are simple for archival/import but require O(n) scans, application-level locking and crash recovery; Java serialization is language-specific and has similar scan/concurrency limits. A database offers indexed ID/route access, isolation and coordinated writes. Campus-local serialized files would require scanning 12 files (O(total n)), duplicate/conflict resolution and file locks; storage remains O(total serialized bytes) and cross-campus consistency is difficult. Measurements from the local H2 test DB are reported as JDBC-engineering evidence, not MySQL performance claims.
